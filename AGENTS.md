# Living Map

A local web app that keeps one live mind map of your Claude Code chat, beside it. It is retired: Anur Living Map (`team/`) replaces it, and its page and skill say so. Linked from a chat with `/living-map`, it follows the chat's transcript as it grows, files what is new (what waits on you, tasks, decisions, what changed in the code) with your own Claude Code, and draws it on a page you work by clicking: lenses for what is waiting, open, decided and changed; answers sent back to the chat; side chats on any box that know the whole chat.

## Stack

- Node 23.6+ runs the server's TypeScript directly (type stripping): no build step for the server.
- Server: Express 5, server-sent events, `node:sqlite`. Browser: React 19, Vite 8, Tailwind 4 (every colour and font in `web/brand.css`), React Flow 12.
- TypeScript 6, strict, one `tsconfig.json` for server, browser and shared code. Tests: Vitest. Lint: ESLint 10 flat config. Format: Prettier (defaults).

## Commands

```bash
npm install
npm start              # build, then serve http://localhost:4317 under server/launcher.ts
                       # (exit code 75 = restart; the launcher still honours it)
npm run dev            # server with --watch, plus Vite on :5173 (?fixture=1 draws a fixture map, no server)
npm run check          # ESLint, tsc, Prettier, Vitest: the same as the pre-commit hook
npm test               # Vitest only
npm run coverage       # Vitest with coverage (report in coverage/); fails when ledger/ drops under the floor in vitest.config.ts
npm run test:ui        # Playwright: the team map's page (playwright.config.ts, a team server copy per file), then the fixture map (playwright.chat.config.ts, its own Vite on :5199) (once: npx playwright install chromium)
npm run upgrade:check  # list dependency upgrades .ncurc.cjs allows (week-old releases, peer- and engine-compatible)
npm run upgrade        # minor and patch upgrades; npm-check-updates doctor reverts any that fail upgrade:test (rewrites package.json and the lockfile; only when asked)
npm run upgrade:latest # the same, majors included (only when asked)
npm run skill          # install both skills, living-map and anur-living-map, into ~/.claude/skills (writes outside the repo; only when asked)
npm run skill -- --hook  # also add the living-map UserPromptSubmit hook to ~/.claude/settings.json (only when asked)
node skill/uninstall.ts [--keep-data|--delete-data]  # take the chat map off this Mac (writes outside the repo; only when asked, and in tests only with HOME, PORT and LIVING_MAP_HOME pointed away)
node eval/read-format.ts             # can models read mermaid+ as well as one line per item (calls the model, ~$0.50; only when asked)
node eval/transcripts.ts [N]         # the transcript reader over your N largest Claude Code chats (local, no model)
node eval/changes-retro.ts [N] [out] # what changed, rebuilt from your N latest sessions (local, no model)
node eval/extract-run.ts --pick 15 [--max-usd 40] [--fresh]  # the extractor over your own chats, offline, with 5 checkpoints each (calls the model; only when asked)
node eval/extract-label.ts [--fresh] <dir>...   # Opus labels each checkpoint (calls the model; only when asked)
node eval/extract-score.ts [<dir>...]           # recall and precision against the labels, and settle.md for your marks
```

The pre-commit hook (husky, `.husky/pre-commit`) runs lint-staged, then the full checks; each check's own exit code decides.

## Verify

```bash
npm run check && npm run build && python3 .github/agent-docs/check.py
```

For a change under `web/` or to `team/live/index.html`, also `npm run test:ui`; for one under `ledger/`, also `npm run coverage`. CI runs both. For one under `mac/`, also `cd mac && swift test && ./build.sh` (CI does not build it).

For a UI change, also try it in the browser on a test server (below), on a linked chat.

## Layout

- `ledger/`: the map of a chat.
  - `transcript.ts` holds a chat as the map's own entries and turns (compactions, queued prompts, sealing, edit patches, the question tool's questions and your picks as `turn.asked`, the agent's task-list changes as `Entry.tasks`, never other tool output): `transcript/entry.ts` is the entry, `transcript/turns.ts` turns entries into turns. The agent reads its own transcript into entries (`AgentConversation.readMore`; for Claude Code, `server/providers/claude-transcript.ts`: uuid dedupe, `logicalParentUuid`, which lines are prompts, task-list tool calls as task steps), and the ledger and side chats are handed that reader.
  - `extract.ts` files new turns as ops: `extract()` on the provider, a fresh `claude -p` with its own system prompt, no tools, no cache and a JSON schema, on Claude Code's default model unless `{"ledgerModel": …}` in `~/.living-map/settings.json` names one; the agent's `judgmentModel` refuses Haiku for judgment. Its instructions list the kinds and states from `KINDS`, `STATES` and `KIND_GUIDE` (`items.ts`), and the whole text is pinned in `ledger/fixtures/extract-system.txt`: change both together. Each run keeps `promptId` (12 hex characters of its instructions and schema) in `runs.prompt`, and `eval/extract-score.ts` scores each id apart. `apply.ts` checks every op (quotes, server-minted ids, who may write what) before it is stored. A state change lands even when its quote fails; a wait closed that way is marked `unconfirmed` (stored, migrated in `db/schema.ts`) and listed under Waiting to check until you or a quoted change settles it.
  - `db.ts` is the store (`~/.living-map/ledger.db`, `node:sqlite`, migrated by `PRAGMA user_version` on open, after a copy to `ledger.db.before-v<N>`): a run's raw answer is saved first, then one transaction applies it and moves the read point. Its tables are the migrations in `db/schema.ts` (a change is a new entry at the end), its row types `db/rows.ts`, its side-chat queries `db/sides.ts`.
  - `follow.ts` follows every linked chat (and measures how long after a turn seals it is filed: `health.filing` and `health.lag` in the view, one log line per run) — a notice (a background task finishing, the map's listener among them) is not a prompt, so what Claude adds to a filed turn after one is filed as more of that turn, from `Conv.readExtent`. `follow/read.ts` reads the transcript, `follow/run.ts` files its turns, `follow/states.ts` is where a follower is (reading its chat, filing it) and the only code that moves it, and both are handed the ledger's shared state (`Ctx` in `follow/follower.ts`); `view.ts` builds `LedgerView` (`shared/ledger.ts`); `tasks.ts` replays the agent's own task list from its task steps; `mermaid.ts` writes and parses mermaid+, the map's text form; `changes/` lifts file diffs into system-level change statements with no model.
  - `routes.ts` starts it all and serves `/api/ledger/view` and `/api/ledger/act`; `link.ts` answers `POST /api/link`; `outbox.ts` holds what the chat should hear (`~/.living-map/conversations/<first id>.json`); `handover.ts` rewrites each chat's handover (`~/.living-map/handover/<first id>.md`, and `handover/projects/<folder>.md` for the chat changed last in that folder) whenever its view is pushed.
  - `sides.ts` runs side chats: one open chat with the provider per side chat (`openChat`: read-only `Read,Grep,Glob`, `--restricted`, no web, the chat's project as cwd plus `~/.living-map/sides/<chat>/` holding the rendered `items.md` and `turns.md`, never a transcript; `chatArgs` in `server/providers/claude-code.ts` holds those arguments and `sides.test.ts` checks them). It proposes only by calling its one tool, `propose_change` (`PROPOSE_TOOL` in `sides/proposal.ts`, handed over as `ChatRequest.propose` and served by `server/providers/tool-mcp.ts`, so a call arrives as a `propose` chat event); that input is checked by `checkProposal` and applied only on `apply-proposal`; `sides/stream.ts` folds what the chat says into the reply.
- `server/`: `index.ts` starts the provider, the ledger and the routes (`http.ts`). Every `/api` route but `GET /api/health` needs the local token (`auth.ts`): kept in `~/.living-map/token` (0600), sent as `X-LM-Token` by the skill, hook and scripts. The page signs in once by the link `/api/link` answers (`/auth?n=<code>&conv=<chat>`, one use, 5 min), which sets a year-long HttpOnly cookie and lands on `/?conv=<chat>`; the cookie alone allows only reads, and the page gets the token for writes from `/api/session` (`web/lib/session.ts`). `POST /api/open` (the map's ⋯ → Open in your browser) mints a fresh link and opens it with `browser.ts`; `POST /auth/here` (the signed-out page's Show my maps) sets the cookie for a page on this machine, by its Origin, with no token. A Host that is not localhost, or an Origin that is another page, is refused. New routes are listed in `auth.test.ts`, which fails until they are.
- The chat hears the map two ways: `POST /api/inbox` when the chat asks for it, or at once through `GET /api/inbox/wait`, where `skill/wait.ts` (a listener the chat keeps running in the background) waits for anything marked `wake`. `GET /api/outline` is the map as text (`ledger/outline.ts`: what matters now first, settled topics folded; `?lens=waiting|open|decided` gives one section).
- `server/providers/`: the agent. `types.ts` is the only seam: `AgentWorker` for the map's own work (`extract`, `openChat` for side chats, `judgmentModel`) and `AgentConversation` for your chats (`findConversation`), together `Agent`; each caller takes only the half it uses. `claude-code.ts` implements it (finding your chats and a resumed chat's new file with `claude-sessions.ts`, reading them with `claude-transcript.ts`, `childEnv` dropping the session variables of the chat that started the server); `skill/` is that agent's skill and hook, and `eval/` reads Claude Code chats with it. Nothing outside the agents' folders starts `claude` or reads `~/.claude` (`server/providers/seam.test.ts`, for everything outside `team/`). Pick another with `LIVING_MAP_PROVIDER`.
- `server/update.ts`: the chat map no longer updates. `GET /api/update` always answers that nothing is available, with the retired notice as `reason`, and `POST /api/update` refuses; the page's **New version available** therefore never shows. `server/launcher.ts` still restarts the server on exit 75, which an older copy's last update uses to start this version.
- `web/`: `App.tsx` signs in; with `?conv=<chat>` it asks `GET /api/ledger/view` for that chat once (`map/probe.ts`) and lazy-loads `map/MapScreen.tsx` (the screen's state and what a click does; its camera is `map/camera.ts`, its smaller pieces `map/ScreenParts.tsx`, and the `use*.ts` hooks beside it hold the tips, the notes, the keys, what is shown and what is new); with no chat it lists every mapped chat (`Chats.tsx`, `GET /api/ledger/chats`), each opening in a new tab. `map/layout.ts` places nodes from the items alone (column = depth, rows in tree order, newest first by `order` key), so a new item never moves a node above it, and `holdView` moves the camera by what moved below so the box you are looking at stays put; `layout.test.ts` holds that over a 300-step growth. Node size follows the pane's width class (`sizeFor`: narrower than 640 px gets `NARROW`), never its exact width.
- `skill/`: the `living-map` skill for users' own Claude Code. `SKILL.md` is a template (`{{APP_DIR}}`, `{{PORT}}`), `install.ts` writes it to `~/.claude/skills/living-map/` (the server rewrites an installed copy on start, never a test server), `start.ts` starts the server detached so it outlives the chat that asked, `hook.ts` (the `UserPromptSubmit` hook) only shows each chat once how to remove the chat map, noting the chats told in `hook-told/` in the data folder (the temporary folder once that is gone), and never calls the server, and `uninstall.ts` takes it all off again: the server on its port (only when the process there runs this app's `server/index.ts`, through its launcher if one runs it), the skill (only a copy `install.ts` marked), every hook ending `# living-map-hook`, and the data folder only when asked.
- `e2e/`: browser tests of the map's screen on the fixture map (`playwright.chat.config.ts`, which starts Vite), and of the team map's page in `team-map*.spec.ts` (`playwright.config.ts`, which starts nothing) (`team-map-system.spec.ts` for system maps, `team-map-trace.spec.ts` for Trace a request), which share `team-map.harness.ts` (a copy of the team server with a sample map per worker, started by `useTeamServer()`); Vitest skips this folder. Vitest's settings for both maps are in `vitest.config.ts`.
- `mac/`: the Living Map Recorder, a Swift menu-bar app that records a meeting, transcribes it on this Mac and sends it to the team map's `/api/meetings` (`team/live/meeting.js`), where one no-tool answer a minute is checked by code (`meeting-draw.js`: quotes, depth, kinds, links) before it is drawn; its `README.md` says how it builds, runs and finds the server. Logo files for it and anything else that needs the Anur mark are in `docs/brand/`: use them, never redraw the logo.
- `team/`: Anur Living Map, the team's shared map of a codebase, kept apart from the chat map above: its server (`team/live/`), the `/anur-living-map` skill (`team/skill/`, copied into `~/.claude/skills/` or Pi's `~/.agents/skills/` by hand or by `npm run skill` (`team/skill/install.js`), and refreshed by its own `open-map.sh` wherever it runs from), login service, landing page and story boards. The chat map's own install and use page is `docs/chat-map.md`. Every action sent to a map is checked against its schema in `team/live/commands.js` before its handler runs (400 naming the field); a new action needs one there (`commands.test.js` fails without it), with kinds as lenient as its handler, and its handler takes `Act<'<type>'>` (`types.d.ts`), the type read from that schema. Who may take it is its row in `team/live/permissions.js`: `mayAct` checks the standing it needs (edit link, member, whole map, Admin) before the handler, which checks what depends on the map (the boxes are in your area, the chat or Action is yours); `permissions.test.js` asks a real map as each kind of person. An error it ignores carries a comment inside the catch saying why, or is logged as `console.error('[map] …')` (`catches.test.js`). Its names are its own: the clone is `ANUR_LIVING_MAP_HOME` (else the older `LIVING_MAP_HOME`), its MCP server `anur-living-map` (an existing `living-map` registration still counts), and its data folder `~/.anur-living-map` (`data-dir.js`; a Mac with only the older `~/.living-map-2` keeps it). Its npm package lists what it ships by pattern in `team/live/package.json`, and `package.test.js` fails when a packed file reaches one that is not packed. Not linted or built here: its tests run with `vitest`, and `tsc -p team` (in `npm run check`) type-checks its JavaScript, tests included, with every strict flag on but `noImplicitAny` (`team/tsconfig.json`). `team/tsconfig.strict.json` adds that flag for everything but the tests: type a new parameter in JSDoc, with the shared shapes in `team/live/types.d.ts`. The map's own work with an agent (Ask Claude, Action preparation and runs, the headless chat) goes through `agent` in `team/live/agent.js`, an `AgentWorker` (`types.d.ts`), and your own chats (following a transcript, finding and opening a chat, the skill's folder, registering the map's MCP server) through `chats` there, an `AgentConversation`; everything that starts `claude` or reads `~/.claude` lives in `team/live/agents/claude-code/`, everything that starts `pi` or reads `~/.pi` in `team/live/agents/pi/`, and another agent is a folder beside them listed in `AGENTS` in `agent.js` (`team/live/seam.test.js` holds `team/` and `e2e/` to that; the `adding-an-agent` skill says how to add one). The map's own work runs on one agent (`LIVING_MAP_AGENT`, else the one whose chat started the server); `chats` combines every agent's (`allChats`), each transcript followed by the agent that `owns` it. Pi has no `--json-schema` or permission hooks: each Pi job loads `agents/pi/extension.js`, which registers the job's MCP servers for that run, a `submit_answer` tool held to the schema, and refuses tools and shell commands outside the job's limits; Pi chats hear the map through `agents/pi/listener.js` (`living_map_listen`), not `wait.js`. The map hands each job its own prompt, schema and MCP servers. A running Action may use only the tools its reviewed brief names plus a fixed read-only set: `runSettings` in `agents/claude-code/run.js` builds a PreToolUse hook (`onlyTools` in `process.js`, run as `tool-hook.js`, also behind preparation) that denies the rest. What each call sends is checked by `action-sends.js`, for every agent: an email's run sends the reviewed message once and nothing else, a step whose tools send mail is an email whatever the model called it (`kindFromTools` in `action-kinds.js`), and a run nobody started may not write to GitHub or the web from its shell. The map's headless chat (`converse`) may use only `mcp.js` pinned to its own map (`drawServer` in `draw.js`), with none of your settings, servers or context files, behind the same kind of hook. While a linked chat answers a request from the map's pane (its listener took it and has not listened again), the `edit` its `living_map_change` sends, which names the chat's session, becomes a proposal for the chat's owner (`isAnswering` in `server.js`). `team/live/draw.js` holds what Claude may draw through `living_map_change` (a new box needs a name and a second line, a line needs a label, a name only finds a box for a line, and changing a box takes its id) and `mcp.js` only sends it; the map treats an `edit` from a program on this Mac, or one naming a chat's session, as Claude's, and a change to a box a person made or changed (`by`, `updatedBy`), or greying out a box Claude did not make, becomes a proposal in the sending chat's pane when it is linked, else the linked chat's (`waitsForApply` in `draw.js`, `edit` in `plan-acts.js`), never drawn; Ask Claude and Auto plan offer a change only by calling `propose_change` (its schema in `team/live/propose.js`, served by `propose-mcp.js`; the agent's `ask` hands back the call's input), never as text in the reply; `check` in `proposal-check.js` holds those proposals to the same, where a line with no label may only be the one line into its box, and offers a reorganize (`tidy`) only when it leaves one tree from the start box (`one-tree.js`; a system map is laid out in layers instead), checked again at Apply. An Action draft made from someone's own words (a chat's tool, a meeting's end) goes only through `fromWords` in `team/live/action-items.js`, whose header lists its checks; it takes the author from where the words came from, never from Claude, and the map then prepares the draft but never executes it. A linked chat's `living_map_my_action` (`myaction` in `chat-acts.js`) and `propose_change`'s `actionItems` both reach it with only the person's own messages as the source (never Claude's replies or tool output). Auto plan drops a box whose name says the same as one the person can see (`sameThing` in `name-words.js`), and a planned Action is never taken as ready: only preparation makes it so (`readPlannedTask`). A system map is drawn from facts code reads, never from the model: `system-facts.js` reads one repo (compiled CloudFormation in `system-facts-cfn.js`, CDK in TypeScript from its source in `system-facts-ts.js` when nothing is compiled, Python through `system_facts.py` run by `python3 -I`, apps and Amplify in `system-facts-app.js`, manifests (packages, Dockerfiles, compose services, OpenAPI routes) in `system-facts-manifest.js`), each fact with where it came from, and `system-links.js` links repos by route, deployed name and resource. `system-draw.js` asks the agent (`answer` on `AgentWorker`) to group those facts into boxes and lines that each cite the facts showing them; `system-check.js` rejects any it cannot check against the facts, names a box from its facts when its name shares no word with them, and describes it from them when its description names code they do not contain, and `system-build.js` builds the levels, with each box's components drawn by code alone; the top level starts at one box code adds for the whole system, with no facts (`system-centre.js`: added to an older map when it opens, never a change a redraw lists, a trace's start, or a repo to hide). "Trace a request" on a box follows the facts the map was drawn from (kept beside it, never sent to a page) hop by hop with no model (`system-trace.js`), and the steps become the box's sequence, cut per viewer like the rest. `system-job.js` runs that for one map in the background (its progress is the state's `drawing`, which never holds folder paths) and `system-routes.js` starts, cancels and retries it, for someone signed in on this Mac only. Repos on GitHub come through `github.js`: each person links their own account with the Anur Living Map GitHub App's device flow (its public client ID only, never a secret in the repo; tokens in the data folder, 0600, never sent to a page), and a repo is downloaded at one commit with its symlinks removed, so the map reads only what that person may read. What each person receives of a system map leaves out the repos they may not read on GitHub (`withoutRepos` in `sharing.js`, applied with `sharedState` and in Claude's view; which repos is `hiddenFor` in `system-job.js`). A side chat on a system map reads its code too (`codeFor` in `system-job.js`, handed to the agent as read-only `dirs`): only repos the asker may read on GitHub, and folders on this Mac only for whoever drew it. An Action there works in its box's repo, inherited from the nearest box up its path that names one (`repoOf` in `system-work.js`): your clone found by its origin, else one cloned for a build with your own git sign-in, under the same rule; a box in no repo has nowhere to run (`cannotRun`). A build, on any map whose repo is on GitHub, is ready and runs only for someone with write access there, asked as them (`canBuild` in `server.js`, `whyNoPush` in `github.js`). `team/live/objects.js` reads a stored map as the objects it is meant to hold (`MapObject` in `types.d.ts`: every box, line and memory with an id, a type, a name and dates) and lists what each lacks; maps are not stored that way yet. The page's script is a module; helpers that need no page live in `page-*.js` modules listed in `page-modules.js` (each imports nothing and declares one name, so Share as a file can write it in place of its import; they are served before any access check, since an import never carries a share link's key), and their tests import them. Tests still cut the rest of `index.html` by the first line of a function (`html.indexOf('function topicGraph(')`), so type a declared function there in a JSDoc line above it and leave that first line as it is; `server.js` is tested through the modules it is built from (`proposal-check.js`, `ask-context.js`, and the action handlers in `*-acts.js`, which `openMap` spreads into its `ACTS`), each taking the map's state through `getState`. Fix a type error with a JSDoc annotation at the start of a line (after other code on the same line it is read as a trailing comment and does nothing), not a change in what runs. Its own README says how it runs.
- A test server: `LIVING_MAP_HOME=<test home> PORT=<not 4317> node server/index.ts` keeps its own store and token and leaves the installed skill alone.

## Releases

`main` is the development branch. Every push to it that passes CI is tagged as a dev build, `dev-0.1.<run>` (the `dev-build` job in `.github/workflows/ci.yml`); a push that changes only `CHANGELOG.md` and `docs/shipping/` runs no workflow at all. A build reaches customers only when a maintainer runs the **Release** workflow by hand (`.github/workflows/release.yml`, Actions → Release; it refuses anyone below admin or maintain on the repo): it tags the chosen dev build, the newest by default, `v0.1.<run>` and publishes a GitHub release. Every copy follows a channel (`team/live/channel.js`): **stable**, the default, updates only to releases; **dev**, for the team, to every dev build too, chosen with `ANUR_LIVING_MAP_CHANNEL=dev` or a `channel` file holding `dev` in the team map's data folder. The retired chat map never updates: a copy that installs the release carrying the frozen `server/update.ts` takes no later one. Never create a `v*` tag or GitHub release any other way, and never run the Release workflow unless the user asks.

## Conventions

- New files are TypeScript: ESLint rejects a `.js` file outside `team/`, whose JavaScript runs as it is (the browser loads some of it, and it needs no install).
- Imports carry their extension (`./follow.ts`, `./App.tsx`); Node needs it for the server, and the browser follows the same rule. ESLint orders them: external, blank line, internal. <!-- agent-docs: ignore -->
- Anything model-specific lives in a provider.
- The model's output is untrusted: check every op before it reaches the store (`apply.ts`, `checkProposal`).
- Colours come only from the roles in `web/brand.css` (`bg-canvas`, `text-ink`, `bg-primary`, `border-success-line`, …): no Tailwind palette colours or hex codes in components. Every role has a light value and a dark one (under `prefers-color-scheme: dark`); set both, with text at 4.5:1 or more on the surfaces it sits on. The logo mark is `web/lib/mark.ts`; the favicon is drawn from it at startup.
- A file holds at most 500 lines of code (ESLint `max-lines`, blank lines and comments not counted). `eslint.config.js` lists the one file still over it: add none. What several test files share (fixtures, a fake process, a scripted model) lives beside them in `<name>.harness.ts`, which is not counted as covered source.
- No `setState` inside effects: derive the value, or reset state when its key changes during render.
- One filled button per screen, marked `data-primary` (an open card or side chat owns it); everything else is outlined or behind a ⋯ (`web/components/More.tsx`). Subject matter Claude wrote (titles, quotes, answers) carries `data-content`, so interface words can be counted apart.
- Copy the user reads says "you", in plain words.

## Never

- Never use `--no-verify`, and never commit on or push to `main` (`.claude/hooks/protect-main.sh`).
- Never commit `out/`, `cache/`, `data/` or anything from `~/.living-map`: they can hold private transcripts and maps.
- Never break `npm ci`, `npm run build` or the launcher's restart: every running copy installs `main` with them.
