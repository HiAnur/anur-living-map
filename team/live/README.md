# Anur Living Map, the server

One small server holds the map; every open window draws the same one, and a click in one window (a Dispute, an Approve) moves them all. With `--project <repo>` the map is drawn from that repo's own files; `--demo` plays the plan-first story from `seed.json` instead, for showing the map. What people decide is written to `outbox.md`, which a Claude Code chat can read back. A linked chat's listener (`wait.js`) gets what is meant for that chat, and with it `chat-rules.md`, the rules for answering it, whenever that chat has not had this version of them yet (otherwise one line says they are unchanged), so a chat that started before an update still works from the current rules; `GET /api/rules` gives the same text, and `open-map.sh` prints it when it opens a map.

```bash
node server.js 4323 --project <repo>    # http://localhost:4323/<repo folder name>/
node server.js                          # your maps, http://localhost:4323 (npm start)
node server.js --demo                   # the plan-first story, http://localhost:4323 (npm run demo)
npx anur-living-map                     # in a repo: checks Node, installs the /anur-living-map skill, starts the map and opens it
```

- `/` is always the list of maps (`/api/maps` gives the same list), with "No maps yet — make one" when there are none; only `--demo` shows the story there. A code folder's map is at `/<folder name>/`. A new map of a folder whose `package.json` names it otherwise (a clone in `repo/` of `shop-api`) takes the package's name instead, when no other map, page or folder answers to it; the choice is kept in `<folder>/.living-map/address`, so no address anyone used ever moves, and the folder's name still reaches the map (pages move to the address, the API answers at both). Every map tab reads "Living Map" until its map loads.
- `npx anur-living-map` needs Node 22.18 or newer on Node 22, or 24.2 or newer: `node:sqlite` runs without a flag from 22.13, and `node users.js` needs `import.meta.main` (22.18, 24.2, never 23). It says so and stops on anything older (`node-version.js`). It installs the skill the same way the one-click update refreshes it (`skill-copy.js`), from the clone it runs in, or the copy `npm pack` puts in the package (`prepack`).
- With `--demo`, open `http://localhost:4323` as yourself, and `http://localhost:4323/?as=Priyanka` in a second window as her.
- **→** / **Space** / **Next ›** moves the story forward for everyone; **←** / **Back** moves it back; the buttons on the cards (Dispute, Confirm, Approve, Flag to Sam) are real clicks that set the step and write to the outbox.
- `?rec` hides the controls; `?chat` shows a mock chat pane (off by default: the real Claude Code chat sits beside the map).
- `curl -s localhost:4323/api/outbox` is what the chat hears; `POST /api/act {"type":"reset"}` starts the story over (both with `--demo`).
- Each address is its own map: `http://localhost:4323/gtm/` is a map called `gtm`, with its API under it (`/gtm/api/state`, `/gtm/api/act`). It starts empty, keeps its state in `maps/gtm/`, and fills from the plans drawn on it.
- On the home page, owners can move named maps and maps linked to code folders to **Trash**, even before opening them. **Undo** restores a just-moved map; **Trash → Restore** restores it later, including older locally archived maps. Code files and online copies are kept. Trashed maps stay out of the list across restarts and old links, and Restore never overwrites another map.
- On the home page, the pin on a map keeps it at the top of your own list, above system maps, whichever way the list is sorted. A pin is yours alone and is kept on the server (`maps/.pinned.json`), so it shows in any browser you sign in from. Your name at the top right opens your role, **Settings**, **Recovery email** and **Sign out**, as on a map.
- **Settings** (`/settings`) shows the signed-in person their name, their role on the team (Owner, for the owner of this install), the email the map has for them and how they sign in. The email is the one Google gave when this browser signed in through Google (kept with the session in `users.db`), else the recovery email verified for a password kept on this Mac, which Settings can add or change where this Mac can send email. The owner also finds **Invite someone** there: a name, and a one-use link to `/login` (good for 7 days) where that person chooses their password.
- With `--project`, the project's own map is at `/<project folder>/`, and `/api/...` still answers for it. Without it, a code folder joins the list the same way (`POST /api/projects`, as `open-map.sh` and `npx anur-living-map` do).
- A code folder's map with nothing on it yet shows one card: **Draw this repo as a system map**, with a line on what the map is for. It draws a system map from that folder on this Mac (or opens the one already drawn from it). **New map → System map** asks where the code is: **A folder on this Mac** lists the code folders this server keeps a map of (repos inside your home folder; a path is never typed in, so the page cannot ask after other folders on this Mac), or **On GitHub**.
- Sign-in: every page asks who you are at `/login` (someone already signed in goes on to their maps). On a new install the first person creates an account there under any name (up to 40 letters, digits, spaces, dots and dashes) and a password (at least 8 characters, kept scrambled in `~/.anur-living-map/users.db`, outside the repo), and owns the install; everyone after joins from the owner's invite, and a name nobody was invited under gets no one in. An install from before owners were kept is owned by the story's Admin, if that name has a password, else by whoever made the first account. A signed-in browser acts only as that person. The API stays open to this Mac's own tools (Claude's plans, the listeners).
- Who owns a map, as its Admin (share links, access, Trash): whoever made it (New map, a loaded file, a system map), or else first opened it; a repo's own map is the install owner's. A map from before keeps the Admins it had, with the owner added. The demo story alone keeps its cast and roles from `seed.json`.
- Passwords on this Mac: `node users.js reset <name>` (or `npx anur-living-map reset <name>`; `--port` for a map not on 4323) prints a one-use link, good for 15 minutes, where that person chooses a new password, so no password passes through a terminal or a chat. "Forgot password?" sends an email instead only where this Mac can send one (`mail.json` or `RESEND_API_KEY`), and shows the command otherwise; "Set up recovery email" appears only then too. `node users.js set <name>` sets a password in a terminal (or from a script with `--password-stdin`), `list` shows who has an account, `owner <name>` hands the install to someone else, and `remove <name>` takes an account away.

A Google address on the login's list signs you in as the name kept there, one of this map's people; anyone else signs in under their Google name, and when that name matches one of the map's people, as `<name> (guest)`, never as that person. The map itself stays on this Mac. `LIVING_MAP_LOGIN_URL` points at another login service; set it empty to turn Google off. A name and password kept there (for someone with no Google account) also works in the sign-in form. Signing in through Google also brings your Google picture, as its address (kept in `users.db`, replaced at each sign-in through Google): it is drawn over your initial on the list of maps, in Settings and on every map you open, for everyone on that map. A picture that will not load leaves the initial.
- Drawing by hand: the Box tool in the dock drags out a box at the size you drag (a click makes one the usual size) and you name it inside that shape; a picked box shows a handle on each corner to resize it; the Line tool drags from one box to another, then takes the words on the line; Pan drags the map from anywhere. A box's card ends in Delete this box (the card asks for confirmation; Delete on a selected box removes it immediately and selects its parent), which asks once, then takes the box and its lines off the map for everyone; History brings it back. A click on a line picks it (it turns blue), and Delete line beside it or the Delete key removes just that line; Claude removes one with `remove_lines` in `living_map_change`, or `unlink` in a chat's change. Level − + goes down to level 0, only the start box: the top-level box (with several, the one with the most boxes under it; on a new map, the first box). The start box of a map's top level is a small empty circle ringed in orange, its name on hover, and the boxes right under it, the main topics, are ordinary boxes; a click on the circle shows only the main topics, and another shows every box again. Inside a box, the start box is drawn as a box, in orange.
- Boxes inside boxes: a box can hold a map of its own, and a box in that map can hold one too, at any depth. **Expand ›** on a box, or a double click, opens it; the path at the top shows every level, each one a way back to it, and **Back** goes up one level. Everything you can do to a box (edit, link, comment, make it an Action, archive it) works at every level, and what someone may see is cut at every level too.
- **New map** on the list of maps asks which kind: a **Default map** (a blank canvas) or a **System map**, drawn from the repos you pick on GitHub. Code reads each repo (compiled CloudFormation, or CDK source in TypeScript or Python; Python and TypeScript handler code; apps; Amplify; manifests: packages, Dockerfiles, compose services and the routes an OpenAPI spec serves) and links them by route and name; your Claude Code groups what code read into at most 20 boxes a repo, citing what shows each box and line, and anything code cannot check is left off. The map starts at a circle for the whole system, named after the map, that code adds (and adds to a system map drawn before it, when it opens): every repo and outside system hangs off it by a straight, faint line, and the calls between them keep their rows. Each repo's box opens into its map, and each of those boxes into its parts, which code draws. The panel over the map shows each repo's stage, the time so far and about how long is left, with Cancel; Draw again (or Redraw at the top, once the panel is closed; both say which repos have new commits since the drawing, among those you can read, which the server also checks by itself every 30 minutes as whoever drew the map, and the list of maps shows as "N repos changed since"; when it finds new commits, the map draws those repos again by itself, quietly, as whoever drew it) reads the newest code and redraws only the repos that failed or changed, and keeps what people did to the map: boxes they added (inside the same box), their words and moves on drawn boxes, Actions (a drawn box with one stays even when the code no longer shows it) and lines they drew while both ends remain. A box drawn again is the same box, never a second one beside it: a repo keeps its one box, and any other box is matched to the one it was by its id or its name, so Claude is also told what the map held before. On a map that already has boxes, what code added or renamed lands at once; what code no longer finds stays on the map, listed in the panel by repo, until an Engineer presses **Apply the changes** (it goes) or **Keep the map as it is**. For GitHub you connect your own account once (a code you enter at github.com; a code that runs out or is denied says so, to try again), install the Anur Living Map app on the organization that holds your code (you name it first: someone who is not its owner only sends a request, and the dialog says it waits for an owner of that organization to approve, until the install shows up), and choose from the repos you can read there; they are downloaded at their newest commit and read the same way. Each person sees only the repos GitHub lets them read: a private repo they can't read is a locked "A private repo" box with nothing inside, its lines without words, in the map, its History, a downloaded copy and what Claude reads for them, and nothing on it can be changed by them; someone not signed in sees only public repos, and a system map holding private repos can't be put online. Redraw and Cancel are for the map's Engineers (an Admin, someone an Admin marks **Make Engineer** in Share, or someone whose role says engineer) and whoever drew it. Drawing a new system map is for the owner of this install, or an Engineer or Admin of any map on this Mac; anyone else sees whom to ask (the install's owner and those Engineers and Admins, else an Admin), with a request to copy, and may still connect GitHub so system maps show them the private repos they can read. A box's side chat reads the code behind it, at the commit the map was drawn from, but only repos you can read on GitHub. **Trace a request** on a box's card follows that box's facts through the code, hop by hop and across repos: a call to a route another repo serves, the function that serves it, what its role may read and write, what a queue or schedule sets off, and functions invoked by name. The steps become the box's sequence, drawn by code with no model, and a step into a repo you can't read says only "A private step". A map drawn before facts were kept asks to be drawn again first. An Action on a box works in that box's repo, which every box inside a repo inherits: your own clone of it on this Mac, found by its GitHub remote, or a clone made once with your git sign-in when it builds; its pull request opens in that repo. A build is ready, and runs, only for someone GitHub lets push to that repo, checked with their own GitHub connection; the pull request is still pushed with this Mac's git sign-in. System maps stay at the top of the list.

Auto plan reads the entire map the person can access, including descriptions, decisions, questions and every descendant, whether it starts from a parent or a leaf. It asks one specific clarifying question only when essential information is missing and different answers would materially change the plan; otherwise it proceeds using the available context. Answers in Side Chat continue the original request with that clarification and the whole map. It looks for gaps in the selected branch without repeating topics already covered elsewhere. Suggestions can attach to the selected box or an existing descendant, so a missing role can appear under Categories. Apply rechecks the destination and duplicates against the current map; invalid destinations are dropped instead of moved to the selected box.

Auto plan proposals classify each new box with `boxType: "topic" | "action"`. Topics organize information or decisions. Actions carry a validated `task`: goal, result, destination, inputs, steps, completion evidence, prerequisite Action IDs, readiness (`ready`, `needs_information`, `waiting`) and blockers with who can resolve them. A specific, checkable result makes an Action; missing information does not make it a Topic. Additions can form deeper branches within the selected branch, without an arbitrary target count. Missing or inaccessible prerequisites, dependency cycles and invalid parents are dropped on proposal and checked again on Apply.

Apply creates real, private Action drafts with their instructions already filled in. It does not call Claude or execute work. Open the Action in Side Chat, review its task details and choose **Prepare**. Prerequisites must have confirmed completion with evidence for their current task before preparation or Execute; dependent Actions show **Waiting on a dependency** and return to a draft when those prerequisites finish. Independent Actions can proceed. Preparation may ask a focused question, and keeps the plan and answers for retry. It checks required tool names against the actual runtime catalog and tool discovery, rather than trusting the planner's readiness claim.

For a map owner, preparation loads the execution project's configured tools. A permission hook allows only file reads/search, web lookup, tool discovery, the supported Gmail read tools and map-context reads. Every other call is denied during preparation, including tools allowed by existing settings. Nonowners retain the restricted read-only catalog. Unavailable tools or denied lookups prevent a ready brief. Execute retains normal execution permission checks, so tool availability is not a guarantee that a later write will be allowed. Actual execution results and their evidence are attached to the Action's Side Chat; retries resume the existing execution chat and check finished work before doing more.

Auto plan starts reading the whole map immediately, without a mandatory goal question. If clarification is needed, reply in Side Chat to continue planning. Proposed topics append after existing children in their branch and use the same columns. The preview shifts later branches down only as needed; Apply keeps those positions and Not now restores the existing layout.

Action box: select a saved topic and turn on the **Info box / Action box** toggle at the top right of its details pane. The label shows the current type. Before anything is written in it, turn it off to return to an Info box; after that, **Cancel Action** (before execution) sets it aside as **Cancelled**, keeping its instructions, answers and versions, and **Prepare again** makes it a draft with its instructions. **Action history**, folded under the Action's header, lists every step the map recorded, newest first: who did it and when, the tools a ready brief and a run were given, how a run ended and how long it took. None of it comes from Claude's words. Box metadata shows the latest step. Write what you want done in **Side Chat**, then press **Enter** or the send arrow. Every stage keeps the name **Action box** and the muted plum box style. New and proposed Action boxes have no status pill until preparation starts. A status pill shows **Preparing**, **Needs clarity**, **Waiting**, **Ready to execute**, **Executing**, **Executed**, **Done, unverified**, **Blocked**, **Couldn't prepare**, **Cancelled** or **Unconfirmed**. **Blocked** is a run that could not go on, which **Continue** picks up; **Couldn't prepare** is a preparation that stopped, which you prepare again. Only a run the map saw finish gets the green **Executed** pill: an email whose to-field is the brief's one recipient, with no one copied, or a pull request GitHub confirms, read from the tool calls the run actually made. When Claude reports a task done that the map could not see, it reads **Done, unverified**, with Claude's account shown apart from the map's confirmation, until its author presses **Confirm done**. Continue tells Claude what the map saw the run already do, so nothing is repeated. A **build** Action never works in the project's own checkout: on Execute the map makes a new branch from the default branch, in its own worktree under the team map's data folder, and runs Claude there. Claude edits, runs checks and may use `gh` as in your own terminal (reading a pull request's comments, replying to them), but cannot push or open the pull request itself. A build that ran on its own may only read with `gh`: commenting on, reviewing or merging a pull request or issue, and `gh api` or `curl` writes, are refused in its shell (`action-sends.js`). When it finishes, the map commits the changes, pushes the branch and opens the pull request, which is the run's confirmation. With no change, no remote, or a remote that is not GitHub, the map says so and leaves the branch. An Admin can **Hand over** an Action to another member who has opened the map and can see its box, except while it is preparing or running. Only the new author can then take it on, and its history records who handed it to whom. When the Actions an Action depends on finish, it prepares itself, with what they produced, and stops at **Ready to execute**. Ready actions have an **Execute** button beneath them. Its author can turn on **Run on its own** in the Action's header (off by default, and off again after a handover): once it is ready, the map presses Execute for them, unless it reaches another person. Reading and changing files here run on their own, and so does a build, whose shell works in its own worktree and whose pull request still waits for a reviewed merge. An email, and any step whose brief needs a connector tool or (outside a build) the shell, stays at **Ready to execute** with the reason (`reach` on the agent, `alone` in `action-kinds.js`). A question during preparation still waits for your answer. A run of an **other** step that only read and changed files here counts as **Executed**, with the files it changed as its confirmation, so a chain of research, drafting and file steps runs through once its first is started. Preparation runs in the background using the whole accessible map, the topic's Side Chat and readable project files. It cannot send messages, change files or fetch web pages. Missing details appear in Side Chat, with the **Needs clarity** pill on the map box. Questions and answers stay in that conversation. Enter submits your action or answer; Shift+Enter adds a new line. Once the goal, destination, steps and expected result are known, its pill reads **Ready to execute** for review. Email tasks include the exact recipient, subject and message. A step whose tools send mail is an email whatever preparation called it, so its message is always reviewed. Its run may send that message once, to that recipient with no one copied and nothing added; any other send is refused before it goes, and the run says why. **Revise** saves the previous reviewed draft as a versioned Markdown file in the Action chat. Download its filename or expand **View document** to read and copy it; saved versions remain through preparation, execution and refresh. The next preparation receives the prior draft with your requested changes. **Execute** runs `claude -p` in the background with configured tools and automatic permission checks, streams its words into Side Chat and keeps its final response there. It never opens the desktop app. **Continue**, with an optional reply, resumes that exact saved chat with `--resume`, including after a refresh or server restart. It never silently starts a fresh chat if a resume fails. Stop interrupts the process; the response describes what actually happened, including missing access, rather than treating process exit as task completion. Old desktop handoffs load as unconfirmed and are never rerun automatically. An Action is one of three kinds: an **email** to one exact recipient, a **build** that ends in a pull request, or **other** work the connected tools allow, which its author confirms done (unless the run only read and changed files here, when its reply and those files are the result). `action-kinds.js` holds that list and what each kind means to the map. Only the person who prepared the action can answer, revise, cancel or execute it. A box holding an Action leaves the map only by its author's or an Admin's hand, never in a change Claude proposes, and never while it is preparing or running. Before it runs, **Delete this box** asks first, naming its Action, and any Action waiting on it stops waiting. Once it has run, it is not deleted but archived: **Archive this box** takes it off the map with its whole record, which still counts for the Actions waiting on it. History lists it under **Archived Actions**, where **Put back on the map** restores it with its lines. Preparation can be cancelled or retried; a changed box must be prepared again. Action details stay local and are excluded from guest links, downloaded map files and cloud sharing.

Action drafts from your words: when you commit to something ("I'll send Dan the pricing by Thursday") where the map hears your own words, the map can make it an Action draft for you, with its task filled in. Claude only proposes the item; `action-items.js` decides, and is the one entry point a chat's tool or a meeting's end calls (`map.fromWords(source, proposed)`, described at the top of that file). It makes a draft only when the quote is in your own words in that source (as typed, or for speech 80% of its longer words), says you will do it ("I'll", "I will", "let me", "on me"), carries a valid task, was not refused before and is not already one of your Actions or action items (then the quote is added to that box instead). The author is always the person whose words they are, never a name Claude writes: an item Claude says is someone else's becomes an info box **for** them. A draft goes under the box Claude named if you can use it, else under a box the map keeps for your items; at most 5 are made a pass and 20 from one source. Its header reads **Made from your words** with the quote. The map then prepares it for you, as you, at most 3 at a time per person, and stops at **Ready to execute** or **Needs clarity**: preparation only reads, **Execute** stays your click, and **Run on its own** stays off. Action history records **Prepared automatically, from your words**. Until it runs, **Not an action** turns it back into an Info box and **Not mine** does the same and names whose it is (one of the map's people, or the team); either stops a preparation under way first, and those words never make an Action on this map again. An info box for someone shows **Take it on** to that person, or to anyone who can see one for the team; the first to press it becomes the author of a draft from the task kept on the box, which the map prepares the same way. Claude's own ideas for Actions stay blue proposals that read **Claude suggests an Action for you** until you press **Apply**. Every item made, merged, refused, undone or prepared goes into the map's log with its reason.

Execution results distinguish **Executed**, **Needs your answer**, **Blocked** and **Completion unconfirmed** in Side Chat. Successful results show a short summary with **View details** for the full reply and supporting confirmation, plus an **Executed** pill on the map box. Executed requires a structured confirmation with concrete evidence; a normal process exit alone does not count. Older desktop handoffs load as unconfirmed and offer **Execute here**, which checks for prior work before finishing anything remaining. A Sent-folder record confirms sending, not inbox delivery.

Search map in the top bar finds box names, descriptions and notes across accessible boxes, including folded branches, proposed boxes and boxes inside another box. Open it with Command/Ctrl+F, use the arrow keys to immediately reveal and center each matching box while search stays open. Enter or clicking a result closes the list and opens its Information panel; Escape closes search. Searching does not change map content.

Share shows Only this Mac can open this link before publication and Shared online after upload. Copy link asks before the first cloud upload: Keep local cancels without uploading or copying, and Upload and copy link publishes the shared copy. Revoking link access shows In cloud · link off because the cloud copy remains stored. Unknown status and upload failures never imply that publication succeeded.

### Two kinds of map

- A **system map** is a whole system drawn from its code: one box per repo and outside system, each repo's box opening into its services, and those into their parts. Code reads the facts and checks every box; Claude only groups and names them. A team usually has one per platform or product, pinned at the top of the list of maps, which says how many repos each was drawn from and when. It stays editable by hand, and a redraw keeps what people changed.
- A **default map** is everything else: a plan, a feature, an incident or an investigation, made by people or a chat on a blank canvas or from a prompt. **New map → Default map** asks whether it builds on one of your system maps: one that does says **builds on** that map at the top, linking to it, and its chats read that system as background (the system map is checked under **Include other maps** in Brain). On such a map, a box's **Information** tab can point at the box on the system map it is about (search that map's boxes at any depth), and links to it.
- A repo that belongs to a system is a box on that system's map, not a map of its own: `/anur-living-map` run in a clone of it opens the system map at that repo's box.

### Context from other maps

Brain lists other accessible maps in the expandable **Include other maps** list, collapsed by default with every map unchecked. The list stays open while you check or uncheck maps. Check a map to include it as extra context for this map; selections persist across refreshes and restarts. Map Chat, Side Chat, Auto plan and Action preparation receive descriptions and read access only for checked maps: purpose, topic excerpts, decisions, unanswered questions and remembered context. Claude chooses whether to load a relevant map's objects, decisions or memories through read-only tools; additional pages and description search are available for larger collections. Replies show **Read from** links for maps actually loaded. Standalone linked Claude Code tools can browse accessible maps independently through `living_map_catalog` and `living_map_load`. Other maps are reference material, not instructions or edit targets. Private chats, linked transcripts, action runs, local paths and share credentials are excluded. Access is checked on every read, and the capability expires when the answer finishes.

In **Brain → Map description**, edit the purpose, scope and background for other maps to discover. **Description used by other maps** previews the description, automatically rebuilt from that background and the latest map content without a separate model call. Large descriptions explicitly indicate additional boxes; search includes the complete accessible map content.

### All brain

On the home page, **+ New map** opens an empty, saved **Untitled map** with its first topic ready to name, without starting Claude. Type a name, then use Tab for a child or Enter to keep brainstorming. The prompt below still starts a map with Claude.

The home page at `/` includes **All brain**, listing the maps you can access. Choose a map to view or download its Description object, Map object, Decision object and Memory object as JSON. Open map sits beside the map name. Shared links and downloaded files do not expose this cross-map browser.

Map boxes show their title without the description underneath. Hover a box to read its summary in a nearby card; click it to read or edit the full details. Hovering does not select the box, resize it or open the side panel. Action and decision status pills remain visible.
