# Anur Living Map, the server

One small server holds the map; every open window draws the same one, and a click in one window (a Dispute, an Approve) moves them all. With `--project <repo>` the map is drawn from that repo's own files; `--demo` plays the plan-first story from `seed.json` instead, for showing the map. What people decide is written to `outbox.md`, which a Claude Code chat can read back. A linked chat's listener (`wait.js`) gets what is meant for that chat, and with it `chat-rules.md`, the rules for answering it, whenever that chat has not had this version of them yet (otherwise one line says they are unchanged), so a chat that started before an update still works from the current rules; `GET /api/rules` gives the same text, and `open-map.sh` prints it when it opens a map.

```bash
node server.js 4323 --project <repo>    # http://localhost:4323/<repo folder name>/
node server.js                          # your maps, http://localhost:4323 (npm start)
node server.js --demo                   # the plan-first story, http://localhost:4323 (npm run demo)
npx anur-living-map                     # in a repo: checks Node, installs the /anur-living-map skill, starts the map and opens it
```

- `/` is always the list of maps (`/api/maps` gives the same list), with "No maps yet — make one" when there are none; only `--demo` shows the story there. A code folder's map is at `/<folder name>/`. A new map of a folder whose `package.json` names it otherwise (a clone in `repo/` of `shop-api`) takes the package's name instead, when no other map, page or folder answers to it; the choice is kept in `<folder>/.living-map/address`, so no address anyone used ever moves, and the folder's name still reaches the map (pages move to the address, the API answers at both). Every map tab reads "Living Map" until its map loads.
- `npx anur-living-map` needs Node 22.18 or newer on Node 22, or 24.2 or newer: `node:sqlite` runs without a flag from 22.13, and `node users.js` needs `import.meta.main` (22.18, 24.2, never 23). It says so and stops on anything older (`node-version.js`). It installs the skill the same way the one-click update refreshes it (`skill-copy.js`), from the clone it runs in, or the copy `npm pack` puts in the package (`prepack`).
- With `--demo`, open `http://localhost:4323` as yourself, and `http://localhost:4323/?as=Priyanka` in a second window as her.
- **→** / **Space** / **Next ›** moves the story forward for everyone; **←** / **Back** moves it back; the buttons on the cards (Dispute, Confirm, Approve, Flag to Sam) are real clicks that set the step and write to the outbox.
- `?rec` hides the controls; `?chat` shows a mock chat pane (off by default: the real Claude Code chat sits beside the map).
- `curl -s localhost:4323/api/outbox` is what the chat hears; `POST /api/act {"type":"reset"}` starts the story over (both with `--demo`).
- Each address is its own map: `http://localhost:4323/gtm/` is a map called `gtm`, with its API under it (`/gtm/api/state`, `/gtm/api/act`). It starts empty, keeps its state in `maps/gtm/`, and fills from the plans drawn on it.

Code files and online copies are kept. Trashed maps stay out of the list across restarts and old links, and Restore never overwrites another map.

Your name at the top right opens your role and **Settings**, as on a map.

Level − + goes down to level 0, only the circle. No box is drawn orange. A click on the circle shows only the main topics, and another shows every box again.
- Boxes inside boxes: a box can hold a map of its own, and a box in that map can hold one too, at any depth. **Expand ›** on a box, or a double click, opens it; the path at the top shows every level, each one a way back to it, and **Back** goes up one level. Everything you can do to a box (edit, link, comment, make it an Action, archive it) works at every level, and what someone may see is cut at every level too.
- **New map** on the list of maps asks which kind: a **Default map** (a blank canvas) or a **System map**, drawn from the repos you pick on GitHub. Code reads each repo (compiled CloudFormation, or CDK source in TypeScript or Python; Python and TypeScript handler code; apps; Amplify; manifests: packages, Dockerfiles, compose services and the routes an OpenAPI spec serves) and links them by route and name; your Claude Code groups what code read into at most 20 boxes a repo, citing what shows each box and line, and anything code cannot check is left off. The map starts at a circle for the whole system, named after the map, that code adds (and adds to a system map drawn before it, when it opens): every repo hangs off it, as does an outside system nothing calls; an outside system something calls hangs under the first repo calling it, a person under the repo they use, and the other calls are curved cross-links, as on any map. A system map whose levels were laid out in rows is laid out this way once when it opens, a level at a time, unless someone moved a box on that level. A click on that circle folds the map to the circle alone, and another shows every box again. The drawing's panel sits in the top left corner, clear of the circle (above the legend in a narrow window). Each repo's box opens into its map, and each of those boxes into its parts, which code draws. The panel over the map shows each repo's stage, the time so far and about how long is left, with Cancel; Draw again (or Redraw at the top, once the panel is closed; both say which repos have new commits since the drawing, among those you can read, which the server also checks by itself every 30 minutes as whoever drew the map, and the list of maps shows as "N repos changed since"; when it finds new commits, the map draws those repos again by itself, quietly, as whoever drew it) reads the newest code and redraws only the repos that failed or changed, and keeps what people did to the map: boxes they added (inside the same box), their words and moves on drawn boxes, Actions (a drawn box with one stays even when the code no longer shows it) and lines they drew while both ends remain. A box drawn again is the same box, never a second one beside it: a repo keeps its one box, and any other box is matched to the one it was by its id or its name, so Claude is also told what the map held before. On a map that already has boxes, what code added or renamed lands at once; what code no longer finds stays on the map, listed in the panel by repo, until an Engineer presses **Apply the changes** (it goes) or **Keep the map as it is**. For GitHub you connect your own account once (a code you enter at github.com; a code that runs out or is denied says so, to try again), install the Anur Living Map app on the organization that holds your code (you name it first: someone who is not its owner only sends a request, and the dialog says it waits for an owner of that organization to approve, until the install shows up), and choose from the repos you can read there; they are downloaded at their newest commit and read the same way. Each person sees only the repos GitHub lets them read: a private repo they can't read is a locked "A private repo" box with nothing inside, its lines without words, in the map, its History, a downloaded copy and what Claude reads for them, and nothing on it can be changed by them; a guest with a link sees only public repos, and a system map holding private repos can't be put online. Redraw and Cancel are for the map's Engineers (an Admin, someone an Admin marks **Make Engineer** in Share, or someone whose role says engineer) and whoever drew it. You draw new system maps on this Mac, as the Admin of every map here. A box's side chat reads the code behind it, at the commit the map was drawn from, but only repos you can read on GitHub. **Trace a request** on a box's card follows that box's facts through the code, hop by hop and across repos: a call to a route another repo serves, the function that serves it, what its role may read and write, what a queue or schedule sets off, and functions invoked by name. The steps become the box's sequence, drawn by code with no model, and a step into a repo you can't read says only "A private step". A map drawn before facts were kept asks to be drawn again first. An Action on a box works in that box's repo, which every box inside a repo inherits: your own clone of it on this Mac, found by its GitHub remote, or a clone made once with your git sign-in when it builds; its pull request opens in that repo. A build is ready, and runs, only for someone GitHub lets push to that repo, checked with their own GitHub connection; the pull request is still pushed with this Mac's git sign-in. System maps stay at the top of the list.
- Share ▸ Share as a file downloads the map as one Markdown file (`<map name>.md`): every box with its notes and decisions, the lines, and what still waits on an answer.
- The faces at the top right are who has this map open right now; the menu under them says who is here and who is not.
- It keeps itself current: run from a git clone on `main` with no changes of its own, the server looks at GitHub when it starts and every ten minutes, moves to the newest build its channel follows, never `main` itself: on the **stable** channel, the default and what customers run, the newest release (a `v*` tag only the Release workflow makes, run by hand by a maintainer); on the **dev** channel, every build CI tagged `dev-*` once a push to `main` passed its checks, releases included. `ANUR_LIVING_MAP_CHANNEL=dev`, or a file `channel` holding `dev` in `~/.anur-living-map`, puts a copy on the dev channel; `ANUR_LIVING_MAP_NO_UPDATE=1` turns updating off, refreshes the skill's copy under `~/.claude/skills` (and `~/.agents/skills` once Pi has one) and starts itself again in its place, but never while Claude is answering, running an Action or drawing a map (it waits until all is quiet); pages and listeners reconnect by themselves. A copy without git (`npx anur-living-map`) is left to npx.
- Started by another app (the Living Map Mac app ships one exact version of this package and Node, and updates them only as app updates): `node server.js 4323 --bundled`, or `ANUR_LIVING_MAP_BUNDLED=1`. It never runs git, pulls or restarts itself, and `/api/version` says `"bundled": true` with the package version; the page's version pill shows that version, says "Updates come with the app", and offers no update. The launching app picks the port (the first argument, or `PORT`; 4323 is what the skill and the MCP server expect), the data folder (`ANUR_LIVING_MAP_DATA`; by default the same folder a clone uses, so the two share people and maps, and only one can hold the port), and the log, by sending the server's stdout and stderr to a file of its choosing (Node's own crash reports go straight there too). SIGTERM stops it cleanly: no new requests, the pages' live connections end, and it exits with 0; a map's `state.json` and History list are always written whole (a temporary file moved into place), so even a kill leaves the last whole version. A second server on a taken port says so and exits with 1. `/anur-living-map` (`open-map.sh`) uses a bundled server answering on its port as it is: no clone, pull, start or restart.
- Any Claude Code chat on this Mac, in any folder, can read and change a map with two tools from `mcp.js`: `living_map_read` and `living_map_change` (boxes, lines, to-dos and questions for a teammate, many in one call, boxes named by id or by name). Registered once with `claude mcp add --scope user living-map -- node <path>/mcp.js`; `LIVING_MAP_URL` points it at another server. A Pi chat gets the same tools, and a listener (`agents/pi/listener.js`, its `living_map_listen` tool) in place of `wait.js`, from its first `/skill:anur-living-map`.
- A meeting can be drawn live: the Living Map Recorder (the Mac app, kept in its own repo) sends what was said to `POST /api/meetings` (a new default map named after the meeting, with a meeting box at its centre, owned by `by`, the person recording), then `/api/meetings/<map>/segments` as it hears it and `/api/meetings/<map>/end`. `meeting.js` keeps the words in the map's `meeting.jsonl` (a line it already has, by speaker, times and words, is dropped and counted as `repeated`, so the recorder may send a batch again when an answer was lost) and, about once a minute of talk, after 12 s of silence, and at the end (a last pass), asks the agent for one fresh answer with **no tools** (`agent.answer`: no tools, none of your settings, no connectors, no session kept), so nothing said on a call can make Claude act: the map's instructions and memory, the meeting's boxes and the lines between them (topics talked about in the last 3 stretches with their lines and notes, the others by title, so a call costs about the same late in a meeting as early), the last two minutes again, and the new talk in (at most a few minutes of it per call, so talk that waited goes a stretch at a time); a fixed list of changes out. `meeting-draw.js` checks every change before anything is drawn: its quote must be in what was said, the map has two levels under the meeting (a topic, then at most 5 points under it; a sixth is sent back to update a point or add a note, the tidy pass trimming the whole meeting at its end, and a box aimed under a point becomes a note on it), finer detail goes into a box's notes as a line of at most about 100 characters with its quote cut to 80 once checked in full (the `note` op; a point whose notes are full passes the note to its topic), a capitalised name in a new box's words (never a day or a month) must be in its quote or be one of the map's people, who records or who speaks, an open question closes only on an `answered` quote found in the talk, as a decision ("Decided · …") or a fact ("Answered · …") as Claude judges (`as`), it links to at most one other box (settles, blocks or answers), it doubles no box, it never changes a box a person wrote, and an action item keeps an owner or a date only when its quote says it (an owner may also be someone speaking or on the map). Claude tags each point a decision, action item, question or fact; the checks and the summary go by that, but every box drawn is an info box (an action item names who and by when in its second line, an open question waits as a to-do), and only the recorder's own commitments become Action boxes, at the end. Each drawing sends a box once, however many ops touched it, and never a new box without a title (`namedOnce`). Refused changes go back once with the reasons and are kept in `meeting.refused`. The talk counts as sent only once an answer landed, so a failed or signed-out call loses nothing and is tried again 30 s later. Each answer's cost adds up in `meeting.cost`; at $20 for one meeting the map stops asking and says so. Each step's line in the recorder's own chat is built by code from what it applied ("Added 2 points, 3 notes; updated 1"), never the model's words, and a second line never repeats its kind word ("Open · Open"), and code rebuilds a "Summary and next steps" box under the meeting from its decision and action boxes. After the last pass, a tidy pass (`meeting-tidy.js`, one more no-tool answer over the meeting's boxes and notes, no talk) is asked to bring the meeting to at most 20 points: it merges boxes that say the same thing (notes, quote and lines move to the one that stays), folds points that settle nothing into their topic's notes, and may promote a note to a point while the topic and the meeting are under their limits and the note's quote is in the transcript; code checks each op, touches only boxes Claude made, keeps decisions, action items and open questions as boxes, asks once more with the refusals when the map is still over the target, says in the chat what it did and whether the target was reached (`meeting.tidy`), and logs each op in `meeting.log` beside the notes added. Code then lays the map out once the way Tidy up does (boxes someone dragged keep their side and order). Then one more no-tool answer lists what the person recording said they will do, from their own "You" lines only, and `action-items.js` makes those their Action drafts (prepared as them, never run), each under the topic of the point Claude named so the map stays two levels, the same check a chat's commitments go through; a recorder name that is not one of the map's people makes none, and the chat says why. The recorder calls its microphone "you" and the Mac's sound "others", so a recorded meeting with no "others" line at all (held in a room, or a call played on another device, where every voice reaches the microphone) makes no drafts either: `meeting.noDrafts` is `one-microphone` and the chat says that you can make an Action yourself from any box. A pasted transcript names who speaks, so it is not held to this. `POST /api/meetings/import` takes a transcript pasted after the meeting ("Name: words" lines; `me` names your own) and draws it the same way, in stretches.

Tidy up uses compact topic spacing: 70px between columns and 35px between short boxes, with 30px more round a box's block of two or more children, so each block reads as its own. Taller names reserve more vertical room, and words on connections can widen their gap. A box Claude or a chat adds takes the place Tidy up would give it without moving the others; when its parent's block has no room for it there, so two blocks would interleave and share a stem (`blockClashes` in `project.js`), the level's boxes take their tidied places instead, keeping each box's side and order, unless someone dragged a box on that level. Branch order and sides stay the same; repeating Tidy up keeps the layout stable. A box with no line to the rest keeps its place and never stops Tidy up: it moves only when it sits on top of the tidied boxes, straight up or down to the nearest clear spot, and loose boxes joined to each other as a small tree are tidied as a map of their own. Every level tidies this way, on every map: round its circle, what nothing leads to hanging off it and every other box under the first box that reaches it, the other lines drawn as curved cross-links; a system map, and each level inside it, is first drawn the same way. A map that is not one tree is tidied on the grid instead, and both that and a new box's place on it look for fewer crossings only up to a fixed amount of work (`CROSSING_CHECKS` in `project.js`, about a second), so a big map never holds up the server.

Trackpad pinch zoom follows the gesture distance, calibrated to a 4% zoom-in change per pixel of wheel delta, with smaller fractional movements and a cap on large jumps. Zoom stays anchored under the pointer. Two-finger scrolling pans the map.

In Share, owners can remove a member from this project (someone who opened it before it came to this Mac). Cloud sharing: when this Mac has a cloud service configured, Share → Publish online uploads the map and copies an HTTPS link. Publishing needs Google: the online copy belongs to the Google account you published with, and only that account, from this Mac, changes who has access, turns the link off or deletes it. Under **Who has access online**, type someone's email, pick **Can view** or **Can edit** and **Add**; each person's role can be changed or removed. The map sends no email: send them the link from **Copy link** yourself. On the online copy they sign in with Google: an address on the list gets its access, with their Google name on their edits, comments and the faces of who is here; any other address sees “Ask <owner> for access” and nothing of the map, so a forwarded link alone gets nobody in. **Anyone with the link can view** (off by default) lets anyone holding the link view it without signing in; editing always needs a listed address. **Turn off link** closes it to everyone, listed or not; turning it on again makes a new link. The Google ID token that proves who publishes lasts about an hour and is kept in memory only (`googleIdentity` in `google.js`); once it is stale, Share asks you to sign in with Google again before the next change, and a login service too old to send one makes Share say it must be updated. An online copy published before Google sign-in keeps its link's view or edit mode (Share says “Old link: anyone with it can edit”) until **Choose who can open it**, or any change made while signed in, claims it. Shared maps remain available while the Mac is off. Boxes, lines, descriptions and comments sync both ways when it reconnects; a conflict keeps both copies and shows an error in Share. Private chats, pending proposals, local paths and sign-in records stay local. See `../cloud/README.md` for deployment and limits. Without cloud configuration, links still point to this Mac and Share says so.

Auto plan reads the entire map the person can access, including descriptions, decisions, questions and every descendant, whether it starts from a parent or a leaf. It asks one specific clarifying question only when essential information is missing and different answers would materially change the plan; otherwise it proceeds using the available context. Answers in Side Chat continue the original request with that clarification and the whole map. It looks for gaps in the selected branch without repeating topics already covered elsewhere. Suggestions can attach to the selected box or an existing descendant, so a missing role can appear under Categories. Apply rechecks the destination and duplicates against the current map; invalid destinations are dropped instead of moved to the selected box.

Auto plan proposals classify each new box with `boxType: "topic" | "action"`. Topics organize information or decisions. Actions carry a validated `task`: goal, result, destination, inputs, steps, completion evidence, prerequisite Action IDs, readiness (`ready`, `needs_information`, `waiting`) and blockers with who can resolve them. A specific, checkable result makes an Action; missing information does not make it a Topic. Additions can form deeper branches within the selected branch, without an arbitrary target count. Missing or inaccessible prerequisites, dependency cycles and invalid parents are dropped on proposal and checked again on Apply.

Apply creates real, private Action drafts with their instructions already filled in. It does not call Claude or execute work. Open the Action in Side Chat, review its task details and choose **Prepare**. Prerequisites must have confirmed completion with evidence for their current task before preparation or Execute; dependent Actions show **Waiting on a dependency** and return to a draft when those prerequisites finish. Independent Actions can proceed. Preparation may ask a focused question, and keeps the plan and answers for retry. It checks required tool names against the actual runtime catalog and tool discovery, rather than trusting the planner's readiness claim.

For a map owner, preparation loads the execution project's configured tools. A permission hook allows only file reads/search, web lookup, tool discovery, the supported Gmail read tools and map-context reads. Every other call is denied during preparation, including tools allowed by existing settings. Nonowners retain the restricted read-only catalog. Unavailable tools or denied lookups prevent a ready brief. Execute retains normal execution permission checks, so tool availability is not a guarantee that a later write will be allowed. Actual execution results and their evidence are attached to the Action's Side Chat; retries resume the existing execution chat and check finished work before doing more.

Auto plan starts reading the whole map immediately, without a mandatory goal question. If clarification is needed, reply in Side Chat to continue planning. Proposed topics append after existing children in their branch and use the same columns. The preview shifts later branches down only as needed; Apply keeps those positions and Not now restores the existing layout.

Action box: select a saved topic and turn on the **Info box / Action box** toggle at the top right of its details pane. The label shows the current type. Before anything is written in it, turn it off to return to an Info box; after that, **Cancel Action** (before execution) sets it aside as **Cancelled**, keeping its instructions, answers and versions, and **Prepare again** makes it a draft with its instructions. **Action history**, folded under the Action's header, lists every step the map recorded, newest first: who did it and when, the tools a ready brief and a run were given, how a run ended and how long it took. None of it comes from Claude's words. Box metadata shows the latest step. Write what you want done in **Side Chat**, then press **Enter** or the send arrow. Every stage keeps the name **Action box** and the muted plum box style. New and proposed Action boxes have no status pill until preparation starts. A status pill shows **Preparing**, **Needs clarity**, **Waiting**, **Ready to execute**, **Executing**, **Executed**, **Done, unverified**, **Blocked**, **Couldn't prepare**, **Cancelled** or **Unconfirmed**. **Blocked** is a run that could not go on, which **Continue** picks up; **Couldn't prepare** is a preparation that stopped, which you prepare again. Only a run the map saw finish gets the green **Executed** pill: an email whose to-field is the brief's one recipient, with no one copied, or a pull request GitHub confirms, read from the tool calls the run actually made. When Claude reports a task done that the map could not see, it reads **Done, unverified**, with Claude's account shown apart from the map's confirmation, until its author presses **Confirm done**. Continue tells Claude what the map saw the run already do, so nothing is repeated. A **build** Action never works in the project's own checkout: on Execute the map makes a new branch from the default branch, in its own worktree under the team map's data folder, and runs Claude there. Claude edits, runs checks and may use `gh` as in your own terminal (reading a pull request's comments, replying to them), but cannot push or open the pull request itself. A build that ran on its own may only read with `gh`: commenting on, reviewing or merging a pull request or issue, and `gh api` or `curl` writes, are refused in its shell (`action-sends.js`). When it finishes, the map commits the changes, pushes the branch and opens the pull request, which is the run's confirmation. With no change, no remote, or a remote that is not GitHub, the map says so and leaves the branch. An Admin can **Hand over** an Action to another member who has opened the map and can see its box, except while it is preparing or running. Only the new author can then take it on, and its history records who handed it to whom. When the Actions an Action depends on finish, it prepares itself, with what they produced, and stops at **Ready to execute**. Ready actions have an **Execute** button beneath them. Its author can turn on **Run on its own** in the Action's header (off by default, and off again after a handover): once it is ready, the map presses Execute for them, unless it reaches another person. Reading and changing files here run on their own, and so does a build, whose shell works in its own worktree and whose pull request still waits for a reviewed merge. An email, and any step whose brief needs a connector tool that sends, posts, replies or changes something, a tool the map does not know, or (outside a build) the shell, stays at **Ready to execute** with the reason (`reach` on the agent, the list of known connector tools in `action-sends.js`, `alone` in `action-kinds.js`). A connector tool on that list that only reads (searching mail, reading a Slack channel) runs on its own. A run nobody started is also refused, call by call, any send it was not reviewed for and any tool the map does not know. When you press Execute, a tool the map does not know may run, and the run's result and its history name it, since the map could not check what it did. A question during preparation still waits for your answer. A run of an **other** step that only read and changed files here counts as **Executed**, with the files it changed as its confirmation, so a chain of research, drafting and file steps runs through once its first is started. Preparation runs in the background using the whole accessible map, the topic's Side Chat and readable project files. It cannot send messages, change files or fetch web pages. Missing details appear in Side Chat, with the **Needs clarity** pill on the map box. Questions and answers stay in that conversation. Enter submits your action or answer; Shift+Enter adds a new line. Once the goal, destination, steps and expected result are known, its pill reads **Ready to execute** for review. Email tasks include the exact recipient, subject and message. A step whose tools send mail is an email whatever preparation called it, so its message is always reviewed. Its run may send that message once, to that recipient with no one copied and nothing added; any other send is refused before it goes, and the run says why. **Revise** saves the previous reviewed draft as a versioned Markdown file in the Action chat. Download its filename or expand **View document** to read and copy it; saved versions remain through preparation, execution and refresh. The next preparation receives the prior draft with your requested changes. **Execute** runs `claude -p` in the background with configured tools and automatic permission checks, streams its words into Side Chat and keeps its final response there. It never opens the desktop app. **Continue**, with an optional reply, resumes that exact saved chat with `--resume`, including after a refresh or server restart. It never silently starts a fresh chat if a resume fails. Stop interrupts the process; the response describes what actually happened, including missing access, rather than treating process exit as task completion. Old desktop handoffs load as unconfirmed and are never rerun automatically. An Action is one of three kinds: an **email** to one exact recipient, a **build** that ends in a pull request, or **other** work the connected tools allow, which its author confirms done (unless the run only read and changed files here, when its reply and those files are the result). `action-kinds.js` holds that list and what each kind means to the map. Only the person who prepared the action can answer, revise, cancel or execute it. A box holding an Action leaves the map only by its author's or an Admin's hand, never in a change Claude proposes, and never while it is preparing or running. Before it runs, **Delete this box** asks first, naming its Action, and any Action waiting on it stops waiting. Once it has run, it is not deleted but archived: **Archive this box** takes it off the map with its whole record, which still counts for the Actions waiting on it. History lists it under **Archived Actions**, where **Put back on the map** restores it with its lines. Preparation can be cancelled or retried; a changed box must be prepared again. Action details stay local and are excluded from guest links, downloaded map files and cloud sharing.

Action drafts from your words: when you commit to something ("I'll send Dan the pricing by Thursday") where the map hears your own words, the map can make it an Action draft for you, with its task filled in. Claude only proposes the item; `action-items.js` decides, and is the one entry point a chat's tool or a meeting's end calls (`map.fromWords(source, proposed)`, described at the top of that file). It makes a draft only when the quote is in your own words in that source (as typed, or for speech 80% of its longer words), says you will do it ("I'll", "I will", "let me", "on me"), carries a valid task, was not refused before and is not already one of your Actions or action items (then the quote is added to that box instead). The author is always the person whose words they are, never a name Claude writes: an item Claude says is someone else's becomes an info box **for** them. A draft goes under the box Claude named if you can use it, else under a box the map keeps for your items; at most 5 are made a pass and 20 from one source. Its header reads **Made from your words** with the quote. The map then prepares it for you, as you, at most 3 at a time per person, and stops at **Ready to execute** or **Needs clarity**: preparation only reads, **Execute** stays your click, and **Run on its own** stays off. Action history records **Prepared automatically, from your words**. Until it runs, **Not an action** turns it back into an Info box and **Not mine** does the same and names whose it is (one of the map's people, or the team); either stops a preparation under way first, and those words never make an Action on this map again. An info box for someone shows **Take it on** to that person, or to anyone who can see one for the team; the first to press it becomes the author of a draft from the task kept on the box, which the map prepares the same way. Claude's own ideas for Actions stay blue proposals that read **Claude suggests an Action for you** until you press **Apply**. Every item made, merged, refused, undone or prepared goes into the map's log with its reason.

Where the map hears your words: a Claude Code chat linked to the map (one that opened it with `/anur-living-map`) calls `living_map_my_action` (`mcp.js`) as soon as you commit to something, quoting you, without asking first. The map takes the call only from a chat linked to it, and not from a chat it runs itself (whose tools leave it out). It checks the quote against that chat's own messages, read from its transcript (what you typed there, never Claude's replies or what a tool, file or web page returned), and what you typed for it in the map's Claude pane, and makes the drafts for that chat's owner, so a teammate's chat never makes one for you (`myaction` in `chat-acts.js`). The tool's answer says what was made, merged or refused and why, and the Claude pane shows **Made N Action drafts from what you said** with **Undo**, which is **Not an action** on each. In Ask Claude and Side Chat, `propose_change` carries `actionItems`, checked against your own messages in that chat: they become drafts at once, with the same notice, while the rest of Claude's change stays a blue proposal until you press **Apply**.

Execution results distinguish **Executed**, **Needs your answer**, **Blocked** and **Completion unconfirmed** in Side Chat. Successful results show a short summary with **View details** for the full reply and supporting confirmation, plus an **Executed** pill on the map box. Executed requires a structured confirmation with concrete evidence; a normal process exit alone does not count. Older desktop handoffs load as unconfirmed and offer **Execute here**, which checks for prior work before finishing anything remaining. A Sent-folder record confirms sending, not inbox delivery.

### Two kinds of map

- A **system map** is a whole system drawn from its code: one box per repo and outside system, each repo's box opening into its services, and those into their parts. Code reads the facts and checks every box; Claude only groups and names them. A team usually has one per platform or product, pinned at the top of the list of maps, which says how many repos each was drawn from and when. It stays editable by hand, and a redraw keeps what people changed.
- A **default map** is everything else: a plan, a feature, an incident or an investigation, made by people or a chat on a blank canvas or from a prompt. **New map → Default map** asks whether it builds on one of your system maps: one that does says **builds on** that map at the top, linking to it, and its chats read that system as background (the system map is checked under **Include other maps** in Context). On such a map, a box's **Information** tab can point at the box on the system map it is about (search that map's boxes at any depth), and links to it.
- A repo that belongs to a system is a box on that system's map, not a map of its own: `/anur-living-map` run in a clone of it opens the system map at that repo's box.

### Context from other maps

On a map, the **Context** panel in the right-hand rail lists other accessible maps in the expandable **Include other maps** list, collapsed by default with every map unchecked. The list stays open while you check or uncheck maps. Check a map to include it as extra context for this map; selections persist across refreshes and restarts. Map Chat, Side Chat, Auto plan and Action preparation receive descriptions and read access only for checked maps: purpose, topic excerpts, decisions, unanswered questions and remembered context. Claude chooses whether to load a relevant map's objects, decisions or memories through read-only tools; additional pages and description search are available for larger collections. Replies show **Read from** links for maps actually loaded. Standalone linked Claude Code tools can browse accessible maps independently through `living_map_catalog` and `living_map_load`. Other maps are reference material, not instructions or edit targets. Private chats, linked transcripts, action runs, local paths and share credentials are excluded. Access is checked on every read, and the capability expires when the answer finishes.

In **Context → Map description**, edit the purpose, scope and background for other maps to discover. **Description used by other maps** previews the description, automatically rebuilt from that background and the latest map content without a separate model call. Large descriptions explicitly indicate additional boxes; search includes the complete accessible map content.
